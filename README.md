# 🛡️ SafeBank Transaction Anomaly Detection Platform

An end-to-end banking security platform that detects unusual transaction behavior
and predicts potential fraud using supervised machine learning and unsupervised
anomaly detection, presented through an interactive Streamlit dashboard.

---

## 1. Project Overview

| | |
|---|---|
| **Industry** | Banking / Financial Services |
| **Problem type** | Binary fraud classification + unsupervised anomaly detection |
| **Data** | Synthetic banking transaction dataset (120,000 transactions / 3,000 customers) generated by `generate_synthetic_data.py` — swap in a real dataset with the same schema at any time |
| **Fraud rate** | ~1.4% (realistic imbalance) |
| **Output** | Per-transaction Risk Score (0–100) + Risk Tier (Low/Medium/High/Critical) surfaced in a live dashboard |

The platform blends two complementary detection strategies:

1. **Supervised classifiers** (Logistic Regression, Decision Tree, Random Forest, XGBoost) — learn *known* fraud patterns from labeled historical data.
2. **Unsupervised anomaly detectors** (Isolation Forest, Local Outlier Factor, One-Class SVM) — flag *novel* transaction behavior that doesn't match any labeled pattern, without needing fraud labels at all.

Both signals are blended into a single **Risk Score** (`src/risk_scoring.py`) that powers the dashboard's alerts, customer risk profiles, and real-time simulation.

## 3. Quick Start

```bash
# 1. Clone / unzip the project, then create a virtual environment
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Run the full pipeline (generates data if missing, then preprocesses,
#    engineers features, runs EDA, trains all 7 models, scores risk)
python run_pipeline.py

# 4. Launch the interactive dashboard
streamlit run dashboard/app.py
```

The dashboard opens at `http://localhost:8501`.

### Running steps individually

```bash
python generate_synthetic_data.py --n_customers 3000 --n_transactions 120000
python src/data_preprocessing.py
python src/feature_engineering.py
python src/eda.py
python src/train_supervised_models.py
python src/train_anomaly_models.py
python src/model_evaluation.py
python src/risk_scoring.py
streamlit run dashboard/app.py
```

### Using your own dataset

Replace `data/raw/banking_transactions.csv` with a CSV containing (at minimum)
these columns, then run `python run_pipeline.py` (it will detect and reuse the
existing raw file):

```
Transaction_ID, Customer_ID, Transaction_Amount, Transaction_Type,
Transaction_Date, Merchant_Category, Location, Device_Type,
Account_Balance, Transaction_Status, Fraud_Label (optional)
```

If `Fraud_Label` is absent, skip `train_supervised_models.py` and rely on the
anomaly-detection models plus a rules-based fallback in `risk_scoring.py`
(see `docs/ARCHITECTURE.md` for the recommended adaptation).

## 4. Data Preprocessing (`src/data_preprocessing.py`)

- **Missing values** — numeric columns imputed with per-transaction-type median; categorical columns imputed with mode.
- **Duplicates** — removed by `Transaction_ID` and by full-row match.
- **Outliers** — IQR-based winsorization (3× IQR) on `Transaction_Amount` and `Account_Balance`, with an `Is_<col>_Outlier` flag preserved as a feature rather than deleting the row (outliers are often the fraud *signal*, not noise).
- **Encoding** — Label encoding on all categorical fields (fitted encoders saved to `models/label_encoders.joblib`).
- **Scaling** — `StandardScaler` on numeric fields (saved to `models/scaler.joblib`).

## 5. Feature Engineering (`src/feature_engineering.py`)

Adds behavior-based features that drive most of the model's predictive power:

| Feature | Description |
|---|---|
| `Amount_Deviation_Ratio` | Transaction amount ÷ customer's historical average |
| `Amount_Zscore_vs_Customer` | How many std-devs this transaction is from the customer's norm |
| `Amount_to_Balance_Ratio` | Transaction amount ÷ current account balance |
| `Minutes_Since_Last_Txn` / `Is_Rapid_Repeat_Txn` | Velocity — rapid repeat transactions are a classic fraud signal |
| `Is_Night_Txn`, `Is_Weekend`, `Txn_Hour` | Time-based risk features |
| `Is_High_Risk_Location`, `Customer_Location_Diversity` | Geographic risk |
| `Is_Cash_Category` | Cash-out / money-transfer / jewelry categories used in laundering |

## 6. EDA (`src/eda.py`)

Generates 10 figures into `reports/figures/`, covering amount distribution,
fraud vs. legitimate comparisons, customer behavior, transaction frequency,
geographic patterns, hourly/weekly/daily time trends, and a correlation heatmap.

## 7. Modeling

### Supervised (`src/train_supervised_models.py`)
Logistic Regression, Decision Tree, Random Forest, XGBoost — all trained with
class-balancing (`class_weight="balanced"` / `scale_pos_weight`) to handle the
~1.4% fraud prevalence. Confusion matrices, ROC curves, and a feature-importance
chart are saved to `reports/figures/`.

### Anomaly Detection (`src/train_anomaly_models.py`)
Isolation Forest (full dataset), Local Outlier Factor and One-Class SVM
(stratified 40k sample for tractability). PCA scatter plots visualize the
detected anomalies for each model.

### Why both?
Supervised models are strong on *known* fraud typologies but blind to novel
attack patterns. Anomaly detectors need no labels and catch drift/emerging
patterns, at the cost of more false positives. Blending both (see below) hedges
against either model's blind spot — a standard pattern in production fraud
systems.

## 8. Evaluation (`src/model_evaluation.py`)

**Accuracy is intentionally de-emphasized** — with a 1.4% fraud rate, a model
that predicts "legitimate" every time scores ~98.6% accuracy while catching
zero fraud. The report and dashboard foreground **Precision, Recall, F1, and
ROC-AUC** instead. Full metrics: `reports/metrics/model_evaluation_report.md`.

## 9. Risk Scoring (`src/risk_scoring.py`)

```
Risk Score = 0.6 × scaled(fraud_probability) + 0.4 × scaled(anomaly_score)
```

| Risk Score | Tier |
|---|---|
| 0–34 | Low |
| 35–59 | Medium |
| 60–79 | High |
| 80–100 | Critical |

Customer-level risk profiles aggregate each customer's transaction-level scores.

## 10. Dashboard (`dashboard/app.py`)

Four pages, navigable from the sidebar:

1. **📊 Transaction Monitoring** — KPIs (total transactions, suspicious count, high-risk customers, fraud %), daily volume/fraud trend, risk tier breakdown, type/category volume.
2. **🔍 Anomaly Visualization** — risk score distribution, fraud-probability-vs-anomaly-score scatter, amount-vs-risk scatter, hour×day risk heatmap, geographic risk bar chart.
3. **⚠️ Risk Analysis** — high-risk transaction alert table (downloadable CSV), customer risk profile explorer, per-transaction fraud-probability gauge.
4. **⚡ Real-Time Simulation** — streams sampled transactions through the live-loaded models one at a time with a progress bar and instant alerting, simulating a production monitoring feed.

All filters (date range, risk tier, location, merchant category) in the sidebar apply globally across pages.

## 11. Deployment Approach

See `docs/DEPLOYMENT.md` for full details. Summary:

- **Streamlit Community Cloud** (fastest path): push this repo to GitHub, connect it at share.streamlit.io, set the app entrypoint to `dashboard/app.py`. Free tier is sufficient for a demo/portfolio deployment.
- **Docker + any cloud VM / ECS / Cloud Run**: a `Dockerfile` pattern is provided in `docs/DEPLOYMENT.md` for containerized deployment behind your own domain and auth layer.
- **Flask API alternative**: for teams that need a headless scoring API (rather than a dashboard) instead of/alongside Streamlit, wrap `src/risk_scoring.py`'s scoring logic in a Flask `/score` endpoint — a starter snippet is included in `docs/DEPLOYMENT.md`.

For real banking use, transaction data and model artifacts must sit behind
authentication, encryption at rest/in transit, and an audit log — this project
folder is a functional prototype, not a compliance-ready system (see Future
Improvements).

## 12. Future Improvements

- **Real-time streaming ingestion** (Kafka / AWS Kinesis) instead of batch CSV scoring, so the risk score updates the instant a transaction posts.
- **Graph-based features** — model money flow between accounts (e.g. with NetworkX or a graph DB) to catch structured/layered fraud rings that per-transaction features miss.
- **Model monitoring & drift detection** — track feature and prediction drift over time and trigger automatic retraining.
- **SHAP explainability** — attach per-transaction SHAP values so fraud analysts see *why* a transaction was flagged, not just the score.
- **Feedback loop** — let analysts label alerts as true/false positive and feed that back into periodic model retraining.
- **Authentication & RBAC** on the dashboard, plus encryption and PII masking for a production banking deployment.
- **A/B testing framework** for comparing risk-scoring blend weights before rolling out changes.
